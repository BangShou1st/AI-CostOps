## Idempotency-Key

需要：

```text
POST /budget-commitments
POST /corrections
```

Server 使用 MySQL `api_idempotency`。

同 Key + 同 Request Hash：

```text
返回第一次成功结果
```

同 Key + 不同 Request：

```text
409 IDEMPOTENCY_KEY_REUSED
```

## Natural Idempotency

不要求调用方传 Key：

```text
POST /charges/{id}/post
POST /expense-claims/{id}/post
POST /imports/{id}/confirm
```

Server 使用 Stable Business Key / Current State 保证重复请求不会重复产生账务结果。

## Optimistic Version

Editable Resource 修改携带：

```json
{"expectedVersion":4}
```

Version 不一致：

```text
409 VERSION_CONFLICT
```

Frontend 遇到 Version Conflict：

```text
重新拉取最新 Resource
→ 提示数据已被其他操作更新
```

禁止自动覆盖。

## State Conflict

例如：

```text
Approve REJECTED Claim
Post CLOSED Period
Confirm SUPERSEDED Allocation
```

返回：

```text
409 STATE_CONFLICT
```

并尽可能返回 `currentState`。

## Budget Concurrency

最终 Guard 是 MySQL：

```sql
UPDATE budget
SET committed_amount = committed_amount + :amount,
    version = version + 1
WHERE id = :budgetId
  AND status = 'ACTIVE'
  AND total_amount - actual_amount - committed_amount >= :amount;
```

Frontend 的“按钮禁用”不能代替此约束。

## Ledger Concurrency

Stable `posting_key` + Unique Constraint 是最终防重复边界。

Redis Lock 不能成为唯一防线。

## Close Concurrency

```text
OPEN
→ CLOSING
```

后普通 Financial Mutation 必须被拒绝。

Close Check 完成后再：

```text
CLOSING
→ CLOSED
```

## Retry Policy

Client 可以 Retry：

```text
Network Failure
明确 503 / 429 且策略允许
幂等 GET
使用 Idempotency-Key 的安全 Create
```

Client 不应盲目 Retry：

```text
Wrong Password
Validation Error
Budget Insufficient
State Conflict
Period Closed
```
