## 2. 上轮 WP6 失败项根因定位与修复验证

上一轮 WP6 曾出现两项硬门禁失败：基线 4 个与新版 9 个非预期 HTTP 502，以及 `multi_budget_single_c100`（-14.5%）和 `multi_org_single_c100`（-18.5%）吞吐下降。本轮通过控制变量与观测补齐，已完成精确根因定位并全部消除：

1. **HTTP 502 归零根因（Mock 压测桩连接队列与短连接缺陷）**
   - **根因**：`scripts/perf/hc01/mock_provider.py` 原直接使用 Python 标准库 `ThreadingHTTPServer`（默认 `request_queue_size = 5`）且未启用 HTTP/1.1 keep-alive（每次响应后直接关闭连接）。在 `c50`–`c200` 并发下出现 accept 队列溢出与 Windows 瞬时端口耗尽，导致 Gateway 侧触发连接异常并判定 `UNKNOWN_POST_DISPATCH`，连续 5 次后拉起 30 秒 Redis 熔断并返回 `502`（`No route candidate can be safely dispatched`）。
   - **修复与验证**：显式子类化 `MockProviderServer(ThreadingHTTPServer)`，设置 `request_queue_size = 512`、`allow_reuse_address = True`、`daemon_threads = True`；为 `Handler` 启用 `protocol_version = "HTTP/1.1"`、`disable_nagle_algorithm = True` 与严格 `Content-Length` keep-alive，同时保留 `http500` / `timeout` / `disconnect` / `hold` / `slow-stream` 故障路径与 `close_connection = True`。修复后，在完整的 6 轮 ABAB（覆盖单预算 `c20`–`c200`、8 预算 `c100`、8 组织 `c100`、Redis 暂停、刷盘模式 2 与到期探针）中，**基线与新版 HTTP 502 均彻底归零（0 / 0）**，无需修改任何 Gateway 业务源码。

2. **多预算 / 多组织 `c100` 此前看似退步的根因（宿主盘同步刷盘漂移 + 502 扰动，而非业务代码退化）**
   - **根因**：上轮基线在新机刚启动阶段以 `autocommit P50 = 9.00 ms` 测得，而新版与 Backend 测试收尾重叠，以 `autocommit P50 = 17.76 ms` 测得；单次成功请求包含多次 InnoDB 提交（`sync_binlog = 1` + `innodb_flush_log_at_trx_commit = 1`），`fsync` 基准相差接近 2 倍，叠加 502 触发的 30s 熔断干扰，掩盖了真实收益。
   - **ABAB 对齐复测结论**：在对齐 `autocommit P50`（`7.20–8.78 ms`、相邻轮次漂移 `3.48%–15.13%`）与 0 个 502 后，`multi_budget_single_c100` **+9.0%**（`61.44 → 66.99 RPS`），`multi_org_single_c100` **+9.8%**（`60.85 → 66.84 RPS`），不存在多预算/多组织代码级退步，因此无需触发 Gateway 代码改动。

3. **S4 观测口径修复（MySQL 8.4 `useServerPrepStmts=true` + Redis `INFO commandstats`）**
   - **实证原因**：在 MySQL 8.4 开启 `useServerPrepStmts=true` + `cachePrepStmts=true` 时，服务端预编译语句通过 `COM_STMT_PREPARE` / `COM_STMT_EXECUTE` 执行（`statement/com/*`），其 `DIGEST` 与 `DIGEST_TEXT` 为 `NULL`，**不会进入 `performance_schema.events_statements_summary_by_digest`**；此前的 `WHERE DIGEST_TEXT IS NOT NULL` 仅能捕获未走预编译的控制语句（约 `16` 次/请求）。
   - **修复方案**：`scripts/perf/hc01/hc04.mjs` 与 `runner.mjs` 改为在压测窗口前后同时采集 `events_statements_summary_by_digest` 与 `performance_schema.prepared_statements_instances` 差值并合并归一统计，同时修正多行 SQL 正则，精准抓出新版 `UPDATE budget SET reserved_amount = reserved_amount + ? ...` 与基线 `SELECT ... FROM budget ... FOR UPDATE` 的独立语句耗时及锁等待耗时；`verify.mjs` 改为输出 Redis `INFO commandstats` 全部业务命令分项次数与单次微秒均值。

## 9. WP6 验证结论

- **负载门禁与根因定位结论**：修复共享 `mock_provider.py` 连接队列与 HTTP/1.1 keep-alive 并在平稳宿主 `autocommit ≤ 30%` 门禁下执行三对 ABAB 交替压测后：**所有场景 HTTP 502 = 0**；单预算 `c20/c50/c100/c200` 成功吞吐提升 **+17.3% ～ +29.6%**，热点预算锁语句耗时由 **145–191 ms 降至 18–19 ms**，8 预算与 8 组织 `c100` 均呈正收益（**+9.0% / +9.8%**）；到期回收 P99 由 **31.46 s 降至 0.98 s**；Redis 暂停窗 502 = 0 且吞吐提升 **+46.1%**。**WP6 负载与根因复核：PASS**。
- **财务一致性结论**：基线 29,373 条与新版 36,212 条 FINAL 用量 100% 1:1 结算并记入 Ledger，0 超扣、0 `budget.reserved_amount` 计数漂移、0 账本/派发违例。**WP6 财务一致性：PASS**。
- **S9 导入规模边界结论**：`10k` / `100k` × 3 全绿；`500k` 独立容器可稳定以 ~5,000 行/s 完成导入与业务断言，但在 **1.86 GiB Docker VM** 约束下，测试收尾 `@AfterEach` 单事务删除 510k 行 `raw_provider_record` 仍存在偶发 `mysql:8.4` `exit=2` 崩溃风险（4 次独立尝试发生 1 次）。**结论保持边界透明：单次 500k 业务导入吞吐已验证，1.86 GiB VM 下大批量清理稳定性存在已知资源限制。**
- **范围边界**：HC-04 阶段 B（分桶配额）门禁状态见 [`bucket-gate.md`](bucket-gate.md)，本文仅覆盖 WP6，不修改 WP7 或 WP8 结论。
