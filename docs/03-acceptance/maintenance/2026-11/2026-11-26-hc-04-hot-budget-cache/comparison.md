# HC-04 WP6 同机 A/B 性能报告

日期 2026-11-26。执行人 Codex。关联 HC-04 WP6，涉及 Gateway、Backend、MySQL 与 Redis。逐轮聚合数据、窗口和 JAR 摘要见 [results.json](results.json)。

## 环境与方法

- 基线 `hc04-baseline` 对应 `927f15e`，应用 V1–V33。新版 `d736469` 应用 V1–V34。两轮分别使用各自的 Backend 与 Gateway JAR。
- Windows 11、Intel Core i9-14900HX、32 逻辑处理器、Docker Desktop 29.8.0 和 1.86 GiB Docker VM。MySQL 8.4.11、128 MiB buffer pool、`sync_binlog=1`，Redis 8.8.1。Gateway Hikari 池和 DB 工作线程各 12，Backend 与 Gateway 均为本机 JVM。
- 先测 1,000 次单行 autocommit INSERT。常规场景每轮热身 8 秒、发压 20 秒，每场景三轮，表格取轮次中位数。成功只计 HTTP 200，RPS 的分母包含最后一批在途请求完成所用时间。每个正式窗口前重置 SQL digest。
- Redis 故障在 40 秒窗口内暂停 30 秒，刷盘模式 2 仅使用独立实验库，结束恢复到 1。到期探针以 25 秒 TTL 发出 20 个真实受控请求，用 MySQL 时间戳计算到期后的回收延迟。
- 新版首两轮 c20 与 Backend 测试收尾重叠，最终 c20 指标使用单独补测。新版的预占探针启动配置修正后继续，结算观察遇到 Windows 错误 10048 后从原数据库和测量窗口续跑。观察查询改走容器内 Unix socket，应用仍按原 JDBC 配置结算。

复现命令和配置见 [HC-04 runner 使用方式](../../../../../scripts/perf/README.md#hc-04-热点预算与缓存-ab)。结果仅用于本机受控条件下的相对比较。

## 指标口径

`Queries` 由 MySQL 全局状态差值计算，包含少量采样查询。文本 digest 在本机对新版使用的服务端预编译语句归集不完整，因此与 `Queries` 并列展示。平均锁等待来自 MySQL 全库 InnoDB 计数，预算等待峰值是 `data_lock_waits` 抽样。基线能从文本 digest 取得预算锁语句耗时，新版对应 SQL 的独立耗时未验证。

## 结算、故障和回收

- 基线 24,275 条和新版 29,073 条 FINAL 用量分别全部结算，每条对应一笔 Ledger Posting 和一条 Entry。两轮超扣和账本一致性异常均为 0，新版预占计数漂移为 0。新版 c20 补测的 3,719 条 FINAL 用量也全部结算，超扣和漂移均为 0。
- Redis 暂停窗口的 HTTP 200 比例由 11.36% 升到 15.48%，其余为 503。已派发的请求数与成功请求数一致。缓存与幂等提示的降级由定向回归验证，故障窗口内仍受现有限流与依赖保护约束。
- 到期回收 P50 由 33.75 秒降到 1.34 秒，P99 由 34.08 秒降到 1.50 秒。各有 20 个样本，均成功转为 `PENDING_HOLD` 后正常结算。
- 单行 autocommit P50/P99 为基线 9.00/40.00 ms、新版首次 17.76/39.30 ms、新版 c20 补测 11.21/26.27 ms。单预算四档成功 RPS 提高 27.8%–52.4%，8 预算和 8 组织分别下降 14.5% 和 18.5%。提交延迟有波动，现有测量不足以定位多预算和多组织的单一瓶颈。
- 在新版的刷盘对照中，单预算 c50 由模式 1 的 35.78 RPS 升到模式 2 的 65.20 RPS。这组结果用于量化刷盘敏感性，正式配置和其他测试均使用模式 1。

## 导入扩展测试

每档保留三个完成行数、金额和发布状态断言的样本。单 Worker、默认批次大小，每 25 ms 采样 JVM 堆，表中堆值为三个样本的最高采样值。

| 输入行数 | 完成轮次 | Worker 行/s 中位数 | 端到端 行/s 中位数 | 堆峰值采样 MiB（最大轮） |
| --- | --- | --- | --- | --- |
| 10,000 | 3 | 4875.67 | 4597.70 | 252.7 |
| 100,000 | 3 | 4947.31 | 4877.34 | 306.8 |
| 500,000 | 3 | 4911.35 | 4768.44 | 503.7 |

组合运行的 500k 首轮由 Worker 记录为 `FAILED`，原测试未采集失败码。500k 定向复跑首轮成功，第二轮的 MySQL 8.4.11 进程以 `signal 11` 退出，Docker 记录 `OOMKilled=false`。其余两个有效样本在新建 MySQL Testcontainers 后分别完成。这三个样本证明单次 500k 导入可完成。同一容器连续运行 500k 的稳定性未通过本次验收。

## 结论

WP6 完成 S1–S9 测量，财务一致性检查 **PASS**，负载验收 **FAIL**。基线和新版的正式窗口分别出现 4 和 9 个 HTTP 502。新版在单预算热点及到期回收上改善明显，多预算和多组织吞吐下降。出现非 FINAL 用量的请求仍保留有效预占，测试中没有按零费用结算。
